What Is an MCP? Making Sense of the Model Context Protocol

A plain-language walk through the Model Context Protocol: why it exists, what actually happens on the wire when a model calls a tool, and what changes once you stop writing integrations and start speaking a protocol.

Ask a chatbot what time it is and, for years, the honest answer was that it had no idea. It could write you a sonnet about clocks, explain how atomic time works, and still not tell you the actual hour, because a language model is a closed room. Text goes in, text comes out, and nothing inside knows anything about the world past its training cutoff.

We have spent the last few years drilling holes in that room. Give the model a function it can call to fetch the time, and suddenly it knows. Give it a function to search your email, and it can find that receipt. Every one of those holes is an integration, and until recently every integration was hand-carved, one at a time, for one model talking to one tool. The Model Context Protocol (MCP) is the idea that we should stop carving holes and agree on a standard door.

The Integration Tax

Here is the shape of the problem, before any protocol enters the picture.

Say you are building an AI assistant. You want it to reach your GitHub, your calendar, and your company's internal wiki. That is three integrations. Each one means learning that service's API, writing the code that translates between what the model asks for and what the API expects, handling that API's particular flavor of authentication, and maintaining all of it as both the model and the API drift over time.

Now your colleague builds a different assistant and wants the same three connections. They write the same three integrations from scratch, because your code was welded to your application. A third team wants GitHub plus Slack plus Notion, and off they go writing again.

Multiply it out and you get an ugly number. With M applications and N tools, the world keeps rewriting toward M times N integrations, most of them near-duplicates of each other. Every team pays the same tax, and the work is never done, because every new tool multiplies against every existing app.

The insight behind MCP is that this multiplication is avoidable. If every application spoke one agreed-upon language, and every tool answered in that same language, an application would need to learn the language exactly once, and so would a tool. M times N collapses to M plus N. The GitHub integration gets written a single time, by whoever knows GitHub best, and every application in the world can use it. This is precisely the trade the web made with HTTP and hardware made with USB: agree on the interface once, and the combinatorial explosion evaporates.

So What Is It, Concretely?

MCP is a specification, published by Anthropic at the end of 2024 and now developed in the open. It is not software you install or a model you call. It is a written agreement about how two programs talk when one of them is an AI application and the other is something that application wants to use.

The agreement covers three things: who the participants are, what they are allowed to say to each other, and the format the words come in. That is genuinely most of it. The protocol is deliberately small, which is a large part of why it caught on.

Strip away the vocabulary and MCP describes an ordinary client-server relationship, the same pattern your browser uses against a web server. An AI application runs a client. A tool or data source runs a server. The client connects to the server, asks what it can do, and then uses it. The novelty is not the architecture, which is decades old. The novelty is standardizing this particular conversation so that any client and any server, written by strangers who never coordinated, can hold it.

A Day in the Life of a Tool Call

The fastest way to understand MCP is to follow one request from start to finish. Picture a coding assistant that has been connected to a server exposing your local filesystem, and you ask it, "What is in my project's README?"

The introduction. Before any of this, when the assistant first launched, its client reached out to the filesystem server and the two performed a handshake. They compared protocol versions and each announced what it supports, the way two devices negotiate before a call. Neither side assumed anything; they agreed on the ground rules first.

The inventory. With the connection open, the client asked the server a simple question: what can you do? The server answered with a list, something like read_file, list_directory, and search_files, each one carrying a plain-English description and a schema spelling out what arguments it needs. The client now holds a menu.

The decision. Your question arrives. The model, looking at that menu of tool descriptions, reasons that answering "what is in my README" means calling read_file with the path to README.md. Note who is deciding here: the model, not you and not the server. It chose the tool because a description told it what that tool was for.

The call and the return. The client sends the request to the server, the server actually reads the file off disk, and it hands the contents back. That text flows into the model's context, and now the model can answer you with the real content of a file it could not have known five seconds ago.

Underneath every one of those steps is the same humble machinery: JSON-RPC 2.0 messages, a decades-old format for one program to call a function in another and get a result. MCP did not invent a wire format. It picked a boring, proven one and agreed to use it consistently, which is exactly the right instinct for a standard.

The Three Things a Server Can Offer

In that story the server offered functions the model could call. Those are the headline feature, but the protocol defines three kinds of thing a server can expose, and the interesting distinction between them is not what they are but who is in control.

Tools are for the model. These are actions the model itself decides to invoke: read a file, open a pull request, run a query. The model reads the descriptions and picks. This is what makes an agent an agent, the ability to choose an action and take it, and it is also where the most care is required, because you are handing the model a lever it can pull on its own.

Resources are for the application. These are pieces of data the host application can choose to load into the model's context, each addressed by a URI like a file path or a database record. The difference from tools is the driver: the application decides to attach a resource, rather than the model deciding to fetch it. Think of the resource as something the app hands the model, versus a tool as something the model reaches out and grabs.

Prompts are for the user. These are prepared templates a person invokes on purpose, usually surfaced as a slash command or a menu item, like "review this pull request." The user pulls them off the shelf deliberately. They encode a workflow someone found worth saving so nobody has to retype the instructions.

The elegance is in that split. The same protocol serves three masters, the model, the application, and the human, and it keeps clear at every moment which one is holding the wheel.

Local Door, Remote Door

One more distinction matters in practice: where the server actually runs. MCP allows two, and the choice is more consequential than it first appears.

A local server runs as a subprocess right on your machine, and the client talks to it over standard input and output, the same pipes a shell uses. Nothing touches the network. This is perfect for a tool that needs your filesystem or a local database, and it is dead simple to ship, because the user just runs a program. The cost is that every user runs their own copy and you have little say over the environment it lands in.

A remote server lives somewhere on the network and speaks over HTTP. Now one deployment can serve many people, you can update everyone at once, and the server can sit in front of a real hosted service. The cost is everything that comes with running a service for other people: authentication, authorization, uptime, and scale become your problem. MCP leans on OAuth for the auth part rather than reinventing it, which is one less wheel to build.

Because the message format is identical either way, the same server logic can often move from the local door to the remote one with little more than a change of plumbing. The conversation is the same; only the hallway changes.

Where the Real Work Hides

Standing up a server with one of the official SDKs takes an afternoon; they handle the JSON-RPC bookkeeping and leave you to write the actual functions. The afternoon is not the hard part. The hard part is that an MCP server is a thing a language model uses, and models use tools through nothing but the words you write to describe them.

There is no other channel. The model cannot read your source, cannot ask you a clarifying question, cannot infer your intent from a variable name. It sees a tool's name, its description, and its input schema, and from that alone it decides whether to call it, when, and with what. A server can be flawless in its code and useless in practice because its descriptions are vague, and this failure is quiet: the tool runs, returns a valid result, and the model simply reached for it at the wrong moment. Most of the craft in building a good server is writing descriptions precise enough that a model reasoning under pressure makes the right call.

The other easy mistake is generosity. It feels natural to expose your whole API, one tool per endpoint, and let the model sort it out. In practice a server with fifty near-identical tools makes the model slower and less accurate, because every tool is another option it has to weigh and every description is more text crowding its context. The better instinct is to design tools around tasks a person actually wants done, even when one such tool quietly orchestrates four API calls underneath. You are designing an interface for a reasoner, not publishing a proxy for your REST routes.

And because a tool can touch real systems, an MCP connection is a genuine trust boundary, not plumbing to wave through. A consequential action deserves an explicit human yes. Inputs deserve validation, because a schema is a request, not a guarantee. And content the model reads through a resource can try to talk it into misusing a tool, so the classic prompt-injection worries follow the data wherever it flows. The safe posture is the boring one: least privilege, clear consent, and a healthy suspicion of anything the model did not write itself.

Why This Is a Bigger Deal Than It Looks

It is tempting to file MCP under plumbing and move on. A standard for tool-calling does not make for a flashy demo. But the standards that reshape how we build are rarely the flashy ones; they are the ones that quietly become assumptions. Nobody markets HTTP. Nobody is excited about USB-C until the day every charger in the drawer suddenly fits.

MCP is aiming at that kind of invisibility. The bet is that connecting a model to the world becomes something you no longer think about, because the connection already exists, written once by someone who cared, and available to every application that speaks the protocol. If that bet lands, the interesting question stops being "how do I wire this model to that tool" and becomes "given that my model can already reach everything, what should it do." That is a much better question to be stuck on, and getting there is the whole point of agreeing on a door.
